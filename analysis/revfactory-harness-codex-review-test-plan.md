# meta-harness 평가계획

작성일: 2026-04-10

## 문서 목적

이 문서는 `meta-harness` 구현물에 대해 **다른 에이전트가 코드리뷰와 테스트를 수행할 때 따라야 할 평가 프레임**을 정의한다.  
핵심은 테스트 구현 방법을 지시하는 것이 아니라, **이번 마일스톤에서 무엇을 검증해야 하고 어떤 근거가 있으면 통과로 볼지**를 명확히 하는 것이다.

## 문서 성격

- 이 문서는 기획/평가 계획이다.
- 테스트 코드 작성 방법이나 개별 assertion 목록을 상세 지시하지 않는다.
- 리뷰 에이전트와 테스트 에이전트는 이 문서를 기준으로 자신의 실행 계획을 세운다.

---

## 1. 현재 마일스톤 정의

현재 `meta-harness`의 평가는 **generation layer MVP** 기준으로 수행한다.

이번 마일스톤에서 평가 대상은 아래에 한정한다.

- `.codex-plugin/plugin.json`
- `skills/meta-harness/SKILL.md`
- `skills/meta-harness/agents/openai.yaml`
- `schemas/harness.schema.json`
- `scripts/scaffold_harness.py`
- `templates/*.j2`
- analysis 문서와 실제 구현 간 계약 일치성

이번 마일스톤에서 직접 출시 게이트로 보지 않는 항목은 아래와 같다.

- 실제 delegated runtime 실행 품질
- `spawn_agent` 기반 오케스트레이션 완성도
- `run_eval.py`, `check_trigger_fit.py`의 완성도
- 고급 `AGENTS.md` 자동 패치 엔진
- 다중 도메인 최적화

즉 이번 평가는 "멀티에이전트 런타임이 완성되었는가"가 아니라, **하네스를 생성하는 계약과 생성기 골격이 제품으로서 성립하는가**를 본다.

---

## 2. 평가 목표

이번 평가의 목표는 아래 다섯 가지다.

1. 생성 계약이 문서, 스키마, 스캐폴더, 템플릿 사이에서 일치하는지 확인한다.
2. 최소한의 generated harness bundle이 안전하고 재현 가능하게 생성되는지 확인한다.
3. generated 산출물이 다른 구현 에이전트에게 넘길 수 있을 정도로 self-contained한지 확인한다.
4. 현재 MVP 범위와 차기 마일스톤 범위가 명확히 분리되어 있는지 확인한다.
5. 이번 단계에서 반드시 고쳐야 할 결함과 후속 이관 가능한 결함을 구분한다.

---

## 3. 평가 역할과 책임

### 3.1 기획/오너

책임:

- 평가 범위를 확정한다.
- 필수 게이트와 차기 이관 항목을 구분한다.
- 최종 승인 또는 반려를 결정한다.

산출물:

- 평가 결과 요약
- 승인 결정
- 후속 액션 지정

### 3.2 코드리뷰 에이전트

책임:

- 구조적 결함, 계약 충돌, 확장성 리스크를 검토한다.
- 단순 스타일 지적보다 제품 성립성에 영향을 주는 이슈를 우선순위화한다.

필수 제출물:

- severity가 포함된 리뷰 리포트
- blocker/high/medium 분류
- 수정 필요 항목과 차기 이관 항목 분리

### 3.3 테스트 에이전트

책임:

- 이번 마일스톤 범위에 맞는 테스트를 설계하고 실행한다.
- 계약 검증, 생성 흐름 검증, 실패 경로 검증에 대한 근거를 남긴다.

필수 제출물:

- 테스트 실행 요약
- 통과/실패 시나리오 목록
- 재현 가능한 실패 케이스
- 미실행 항목과 그 사유

### 3.4 설계 승인자

책임:

- 코드리뷰 결과와 테스트 결과를 합쳐 최종 판정을 내린다.

필수 제출물:

- `pass`, `conditional pass`, `fail` 중 하나의 판정
- 판정 근거 3~5개

---

## 4. 평가 게이트

이번 마일스톤의 평가는 아래 4개 게이트로 나눈다.

### Gate A. 계약 일치성

질문:

- 문서, 스키마, 템플릿, 스캐폴더가 같은 제품 계약을 말하는가

중점 항목:

- skill 메타데이터 규약 일치
- schema와 scaffold 기본 출력의 정합성
- 템플릿과 generated 구조의 경로 계약 일치
- analysis 문서와 실제 코드의 드리프트 여부

통과 조건:

- 구현 에이전트가 문서와 코드 중 무엇을 보더라도 서로 다른 산출물을 만들지 않는다.

실패 조건:

- 문서 예시와 실제 스키마가 충돌한다.
- scaffold 기본 출력이 schema를 만족하지 않는다.
- generated skill/role/pointer 계약이 서로 어긋난다.

### Gate B. 생성 안전성

질문:

- 생성기가 잘못된 파일 상태나 위험한 덮어쓰기를 만들지 않는가

중점 항목:

- 비어 있지 않은 대상 디렉터리 처리
- `force` 동작의 예측 가능성
- 실패 시 손상된 중간 상태 최소화
- 상대경로/루트 경계 준수

통과 조건:

- 생성 작업이 안전하게 중단되거나, 의도된 범위 안에서만 파일을 생성한다.

실패 조건:

- 사용자가 예상하지 못한 덮어쓰기가 발생한다.
- 생성 실패 후 복구하기 어려운 중간 상태를 남긴다.
- 루트 밖 경로나 절대경로가 산출물 계약에 섞인다.

### Gate C. 생성 산출물 사용성

질문:

- 생성된 하네스 골격이 후속 구현 에이전트에게 실제로 넘길 수 있는 수준인가

중점 항목:

- minimal valid harness 생성 가능 여부
- generated bundle의 self-contained 정도
- single-agent fallback 전제의 명시성
- portable bundle로서의 일관성

통과 조건:

- 최소 1개 샘플 하네스를 생성했을 때, 후속 구현 에이전트가 구조를 다시 설계하지 않고 이어서 작업할 수 있다.

실패 조건:

- generated bundle만으로는 후속 구현이 불가능하다.
- 핵심 파일이 빠져 있거나 역할이 모호하다.

### Gate D. 차기 마일스톤 준비도

질문:

- 이번 MVP를 깨지 않고 다음 단계로 확장할 수 있는가

중점 항목:

- delegated mode readiness
- `AGENTS.md` 증분 반영 가능성
- eval runner 확장 가능성
- schema 확장성

통과 조건:

- 다음 단계 확장을 위해 구조를 전면 재설계할 필요는 없다.

주의:

- Gate D는 이번 마일스톤의 참고 게이트다.
- Gate D 이슈는 설계상 치명적인 경우가 아니면 즉시 반려 사유가 아니다.

## 5. 평가 범위별 필수 질문

리뷰 에이전트와 테스트 에이전트는 최소 아래 질문에 답해야 한다.

### 5.1 Skill / Plugin

- `meta-harness` skill은 Codex에서 발견 가능한 형식을 갖추고 있는가
- skill 본문이 generation layer MVP의 목적을 정확히 설명하는가
- generated skill과 meta-harness 자기 자신의 skill이 혼동되지 않는가

### 5.2 Schema

- 현재 schema가 generated harness의 진실 원천 역할을 할 수 있는가
- required 필드와 기본 출력이 실제 사용 흐름과 맞는가
- 차기 runtime layer를 붙여도 schema를 크게 깨지 않고 확장 가능한가

### 5.3 Scaffold

- scaffold는 invalid skeleton을 만들지 않는가
- 동일 입력에 대해 재현 가능한 결과를 내는가
- 실패 경로가 명확한가

### 5.4 Templates

- 템플릿 결과물이 파서와 사람 모두에게 읽기 쉬운가
- optional 필드가 없어도 포맷이 깨지지 않는가
- generated role/skill/eval/pointer가 하나의 번들처럼 맞물리는가

### 5.5 Docs vs Code

- 전략 문서와 실제 코드 사이에 아직 남은 계약 충돌이 있는가
- 현재 문서만 보고 구현했을 때 오해할 만한 지점이 있는가

---

## 6. 필수 평가 시나리오

다른 에이전트는 최소 아래 시나리오를 평가해야 한다.

### 시나리오 1. 신규 하네스 생성

목적:

- generation layer MVP가 성립하는지 확인

확인할 것:

- 최소 샘플 하네스 생성 가능 여부
- 핵심 산출물 세트 존재 여부
- generated bundle handoff 가능 여부

### 시나리오 2. 잘못된 입력 또는 불완전 입력

목적:

- 계약 위반을 제대로 감지하는지 확인

확인할 것:

- schema 위반 처리
- scaffold 실패 메시지 명확성
- invalid skeleton 생성 여부

### 시나리오 3. 기존 대상 디렉터리 재실행

목적:

- 생성 안전성 확인

확인할 것:

- 안전한 중단 또는 명시적 overwrite 경로
- 예측 가능한 재실행 동작

### 시나리오 4. 후속 구현 에이전트 handoff

목적:

- generated 산출물 사용성 확인

확인할 것:

- 다른 에이전트가 generated bundle만 보고 다음 구현을 이어갈 수 있는지
- 설명 부족으로 재설계가 필요한지 여부

## 7. 평가 결과 분류 기준

### 7.1 Blocker

아래 중 하나면 즉시 반려 대상이다.

- scaffold가 schema와 구조적으로 충돌한다
- generated bundle이 최소 사용 형태를 만들지 못한다
- 안전하지 않은 파일 쓰기 동작이 있다
- skill 계약이 깨져 Codex 사용 흐름 자체에 진입하지 못한다

### 7.2 High

출시 직전 반드시 판단해야 하는 항목이다.

- 문서와 코드 계약이 크게 어긋난다
- generated skill/role/template 중 핵심 산출물이 불완전하다
- 사용자가 이해하기 어려운 출력이 발생한다

### 7.3 Medium

출시를 막지는 않지만 차기 액션으로 반드시 이관해야 한다.

- 확장성 제약
- 불완전한 기본값 정책
- 차기 delegated mode 설계 리스크

### 7.4 Low

후순위 개선 항목이다.

- 표현 개선
- 문서 정돈
- 샘플 확대

---

## 8. 승인 기준

### Pass

아래를 모두 만족해야 한다.

- Gate A, Gate B, Gate C 통과
- blocker 없음
- high 이슈 없음
- 후속 구현 에이전트 handoff 가능

### Conditional Pass

아래 조건에서 허용한다.

- Gate A, Gate B는 통과
- Gate C에 경미한 보완 필요
- blocker 없음
- high 이슈는 있으나 범위와 수정 계획이 명확함

### Fail

아래 중 하나면 반려한다.

- Gate A 실패
- Gate B 실패
- blocker 존재
- 생성 산출물이 handoff 불가능

---

## 9. 필수 제출물

최종 평가 전에 아래 산출물이 있어야 한다.

- 코드리뷰 리포트 1부
- 테스트 결과 요약 1부
- blocker/high/medium 목록
- pass / conditional pass / fail 판정문
- 차기 이관 항목 목록

형식은 자유지만, 최소한 아래는 포함해야 한다.

- 무엇을 검토했는가
- 어떤 증거로 판정했는가
- 지금 고쳐야 할 것과 다음으로 넘길 것을 어떻게 나눴는가

---

## 10. 이번 마일스톤의 권장 판정 관점

이번 단계에서는 아래 관점을 유지하는 것이 중요하다.

- "런타임이 완성됐는가"보다 "생성기 MVP가 성립하는가"를 본다.
- "모든 미래 기능이 준비됐는가"보다 "차기 확장을 가로막는 구조적 결함이 있는가"를 본다.
- 세부 테스트 개수보다 **계약 충돌과 handoff 가능성**을 더 중요하게 본다.

즉 이번 평가의 핵심 질문은 하나다.

**현재 구현이 다른 에이전트에게 넘길 수 있는 최소 제품 골격인가**

이 질문에 긍정적으로 답할 수 있으면 pass 또는 conditional pass, 아니면 fail이다.
